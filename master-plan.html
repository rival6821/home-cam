요약 및 준비물

시스템이 하는 일과 하지 않는 일, 그리고 시작 전 준비물을 먼저 확정한다.

이 시스템이 하는 일

구형 폰의 카메라를 WHIP으로 VPS에 올리고, VPS가 WHEP으로 뷰어에 재분배한다. 녹화는 뷰어 브라우저의 로컬 다운로드로만 이뤄지며, 서버·VPS 어디에도 영상이 남지 않는다.

이 시스템이 하지 않는 일

클라우드 저장, 이벤트 감지 알림, 모션 트래킹은 범위 밖이다. 목적은 실시간 원격 시청이며, 중앙 서버(VPS)는 영상을 중계만 하고 기록하지 않는다.

VPS 사양 산정 근거 — 왜 최소 사양으로 충분한가

MediaMTX는 WHIP으로 받은 스트림을 트랜스코딩 없이 그대로 WHEP으로 넘기는 패스스루 구조다. CPU는 SDP 협상과 패킷 포워딩에만 쓰이므로 인코딩 서버 대비 부하가 한 자릿수 낮다. 병목은 CPU가 아니라 아웃바운드 트래픽 총량이며, 이는 §1.4에서 정량 산정한다.

무과금 원칙을 지키는 구체적 옵션: Oracle Cloud Free Tier — VM.Standard.E2.1.Micro(1/8 OCPU·RAM 1GB, x86, 2대까지 영구 무료) 또는 VM.Standard.A1.Flex(ARM64, 영구 무료 한도 2026-06-15 기준 2 OCPU·RAM 12GB로 조정됨) 중 하나면 이 워크로드에 여유 있게 충분하다. 아웃바운드 10TB/월 무료, 인바운드는 무제한·무과금이다. 이미 보유 중인 다른 VPS가 있다면 그대로 사용해도 무방하며, 이 문서의 설계는 특정 벤더에 종속되지 않는다.

먼저 읽기

이 설계는 3가지를 정직하게 감수한다. ① VPS가 미디어를 평문으로 경유한다(§1.5) — 대신 제3자 노출은 P2P 초안보다 오히려 줄어든다. ② 카메라 화면은 24시간 켜져 있어야 한다(§3.2) — 브라우저 기반 송출의 구조적 한계다. ③ 영상은 Cloudflare가 아닌 VPS에서 직접 서빙한다(§5) — 무료 CDN의 영상 트래픽 약관 제약을 피하기 위함이다.

Oracle Free Tier는 인바운드를 과금하지 않으므로 "VPS 트래픽 캡"은 온디맨드를 채택하는 실제 이유가 아니다. 온디맨드를 기본으로 권고하는 진짜 근거는 카메라 폰의 24시간 연속 인코딩·무선 송신이 만드는 발열과 배터리 소모이며, 이는 §3.2의 구조적 한계와 직결된다. 트래픽이 병목이 되는 경우는 인바운드까지 과금하는 다른 VPS 상품을 쓸 때뿐이다.

1:N 확장성. 동시 시청자 5명이 매일 1시간씩 본다고 가정해도 VPS 아웃바운드는 0.5MB/s × 3,600s × 30일 ≈ 52.8GB/월로 10TB 캡의 1% 미만이다. 시청자 수 증가의 부담은 더 이상 카메라가 아니라 VPS가 지며, VPS는 이를 흡수하도록 설계되어 있다.

1.5Zero-Knowledge 원칙 재검증

P2P 초안은 미디어가 진짜 종단간(E2E)이었지만 브로커가 SDP 지문을 중계해 이론상 MITM이 가능했고 양측 IP가 브로커에 노출됐다. VPS 안은 서버가 DTLS를 종단하므로 평문에 접근할 수 있다 — 그러나 그 서버는 본인 소유이며, 외부 구간은 WireGuard로 이중 암호화된다.

02

크로스 플랫폼 엔지니어링 사양

Android Chrome(송출)과 iOS Safari(시청) 사이의 실제 호환성 격차를 메우는 구체 사양.

2.1코덱 정합성 — 가장 흔한 실패 지점

구조적 제약

MediaMTX는 트랜스코딩을 하지 않는다. 카메라가 보낸 코덱과 뷰어가 요구하는 코덱이 다르면 연결은 성공하지만 화면만 검게 나오는 진단하기 어려운 증상이 발생한다(§7 최빈 장애). 해결책은 양단을 H.264 Constrained Baseline(profile-level-id=42e01f)로 강제 고정하는 것이다.

// 카메라(송출) 측 — 비디오 트랜시버에 H.264만 남기고 우선순위 고정
const tx = pc.getTransceivers().find(t => t.sender.track?.kind === 'video');
const h264 = RTCRtpSender.getCapabilities('video').codecs
  .filter(c => c.mimeType === 'video/H264'
    && c.sdpFmtpLine?.includes('profile-level-id=42e01f'));
tx.setCodecPreferences(h264);

참고: SDP 문자열을 직접 잘라 붙이는 방식보다 setCodecPreferences()가 표준적이고 안전하다. 오디오는 양 브라우저 모두 WebRTC 스택 자체에서 Opus를 기본 지원하므로 별도 강제가 필요 없다. H.264는 iOS의 하드웨어 디코더를 타므로 뷰어 배터리 소모도 소프트웨어 디코딩 대비 낮다.

2.2iOS WebKit(Safari) 제약 극복

  • <video playsinline muted autoplay> 3종 속성 동시 지정 — 하나라도 빠지면 자동재생이 차단된다.
  • 오디오 언뮤트는 반드시 사용자 제스처 안에서: 탭 이벤트 핸들러 내부에서 videoEl.muted = false 실행 → 이후 audioCtx.resume() 순서로 호출.
  • 전체화면: iOS는 표준 Fullscreen API를 <video>에서 지원하지 않으므로 videoEl.webkitEnterFullscreen?.() ?? videoEl.requestFullscreen() 형태로 분기.

뷰어가 "녹화" 버튼을 누르면 화면의 <video> 스트림을 브라우저가 로컬 파일로 저장한다(서버 미경유).

2.4해시 딥링크 + QR 원클릭 접속

https://cam-vps.tailXXXXX.ts.net/#cam=livingroom&pin=XXXXXXXXXX 형태의 URL을 QR로 배포한다. URL 프래그먼트(#) 뒤는 브라우저가 서버로 전송하지 않으므로 PIN이 Caddy·MediaMTX 접근 로그 어디에도 남지 않는다. 멀티 카메라는 경로만 바꾼 별도 딥링크(#cam=bedroom)로 자연 분리된다 — 채널 분리용 별도 로직이 필요 없다.

3.2화면 렌더링 부하 최소화

구조적 한계

브라우저 WHIP 송출은 화면·탭이 포그라운드여야 카메라 캡처가 유지된다 — Chrome이 백그라운드 전환 시 타이머를 스로틀링하고 캡처를 중단하기 때문이다. 네이티브 RTSP 앱이었다면 화면을 완전히 껐겠지만, 단일 파일 웹앱 원칙을 지키는 대가로 이 비용은 제거할 수 없다. §1.4의 온디맨드 설계가 줄이는 것은 캡처·인코딩·무선 송신 부하이지, 화면 점등 자체가 아니다.

  • 화면은 #000 풀스크린 오버레이 + 기기 최저 밝기로 OLED 서브픽셀을 최대한 소등한다.
  • <video>를 display:none 처리하면 일부 기기에서 트랙이 정지되므로, 화면은 오버레이로 가리고 엘리먼트 자체는 렌더링 유지한다.
  • 상태 텍스트(연결됨/시청자 수)를 5분 주기로 1~2px 이동시켜 번인을 완화한다.

04

보안 및 접근 제어

Tailscale이 만드는 위협 모델의 변화와, 그 위에 남겨두는 다층 방어.

위협 모델 재정의

이 시스템은 공인 인터넷에 어떤 포트도 노출하지 않는다. 공격자는 tailnet에 이미 속한 기기가 아니면 MediaMTX에 패킷 한 개도 보낼 수 없다 — 브루트포스 공격면 자체가 소멸한다. 따라서 PIN의 역할은 "외부 침입 차단"에서 "tailnet 내부 채널 구분과 오접속 방지"로 바뀐다. 다만 계정 침해 등으로 tailnet 접근권이 뚫리는 최악의 경우를 대비해 PIN 계층은 그대로 유지한다.

4.110자리 PIN 엔트로피 분석

Base32(Crockford, 혼동 문자 I/L/O/U 제외, 32개 기호) 10자리 = 32¹⁰ = 2⁵⁰ ≈ 1.13 × 10¹⁵가지.

공격 시나리오속도전수조사 소요 시간
레이트리밋 적용(10회/분/IP)10 req/min약 2억 1,400만 년
무제한 가정(참고용, 실제로는 tailnet 밖에서 도달 불가)1,000,000 req/s약 35.7 년

4.2MediaMTX 경로별 인증 설계

카메라 계정은 게시(publish)만, 뷰어 계정은 읽기(read)만 허용해 권한을 최소화한다.

# mediamtx.yml
authInternalUsers:
  - user: cam-livingroom
    pass: <10자리 PIN>
    permissions:
      - action: publish
        path: livingroom
  - user: family-viewer
    pass: <별도 시청용 PIN>
    permissions:
      - action: read
        path: ~   # 전체 경로(카메라) 읽기 허용

경로 이름(livingroom, bedroom 등)과 PIN 모두 ASCII 화이트리스트(/^[A-Za-z0-9_-]{1,32}$/)로 검증해 한글 등 비ASCII 입력을 원천 차단한다.

4.3접속자 식별 및 강제 종료

MediaMTX의 HTTP 제어 API(/v3/paths/list, /v3/rtspconns/kick/{id} 등 API 계열)로 현재 세션 목록을 조회하고 특정 연결을 강제 종료할 수 있다. 뷰어 페이지에 "현재 시청자 N명" 표시와 관리자 전용 강제종료 버튼을 둔다.

Docker와 인증

MediaMTX 기본값은 "로컬호스트 요청은 인증 없이 허용"이지만, 컨테이너로 구동하면(§5.1) 이 예외가 성립하지 않는다 — 호스트의 127.0.0.1에서 온 요청도 Docker의 포트 포워딩(NAT)을 거치며 컨테이너 안 MediaMTX에는 브리지 게이트웨이 IP로 찍히기 때문이다. 그래서 action: api 권한을 가진 전용 계정(homecam-admin)을 별도로 두고, API를 쓸 때마다 curl -u homecam-admin:<PIN> ...로 인증한다 — 이 PIN은 게시·시청 PIN과 다른, 운영자만 아는 값이다.

05

VPS 배포 및 PWA 운영 절차

Cloudflare Pages 대신 VPS에서 정적 파일과 미디어를 동일 출처로 서빙한다.

금지

Cloudflare Tunnel로 24/7 영상을 흘려보내지 않는다. 무료 CDN 플랜은 Cloudflare 자체 서비스(Stream/R2 등) 외부에서 호스팅된 영상·대용량 트래픽에 제약을 둔다. 이 설계는 애초에 HTML도 VPS가 직접 서빙해 CORS·혼합 콘텐츠 문제를 원천 차단한다.

5.1배포 5단계 체크리스트

1. VPS 초기 하드닝

SSH 키 전용 접속, 방화벽 기본 차단.

adduser opsuser && usermod -aG sudo opsuser
# /etc/ssh/sshd_config
PasswordAuthentication no
ufw default deny incoming
ufw default allow outgoing

2. Tailscale 설치 및 HTTPS 인증서 발급

curl -fsSL https://tailscale.com/install.sh | sh
tailscale up
# 관리 콘솔에서 MagicDNS + HTTPS Certificates 활성화 후
tailscale cert cam-vps.tailXXXXX.ts.net

3. Docker 설치, MediaMTX 컨테이너 준비

MediaMTX·Caddy는 컨테이너로 구동한다. Tailscale은 인증서 발급이 호스트의 tailnet 신원에 묶여 있어 호스트에 네이티브로 남긴다(아래 콜아웃 참고). WHIP/WHEP 활성화, 녹화 기능은 명시적으로 끈다.

curl -fsSL https://get.docker.com | sh

# mediamtx.yml 핵심 항목 — 호스트의 /etc/homecam/mediamtx.yml에 두고 컨테이너에 마운트
webrtc: yes
webrtcAddress: :8889   # 호스트에는 게시하지 않음 — caddy 컨테이너만 내부망으로 접근
record: no   # 무저장 원칙 — 디스크 기록 자체를 비활성화

4. Caddy로 동일 출처 통합

정적 HTML과 MediaMTX 리버스 프록시를 하나의 HTTPS 오리진으로 묶는다. 두 컨테이너는 Docker 내부 브리지 네트워크로만 통신하고("mediamtx"는 컨테이너 이름이 아니라 Compose 서비스명 — Docker 내장 DNS가 풀어준다), 공인 인터넷에는 아무것도 게시하지 않는다. 포트는 기본 443이지만 고정값은 아니다 — 접근이 어차피 Tailscale로 걸러지므로, VPS를 다른 서비스와 같이 쓰다가 443이 이미 점유돼 있으면(예: 기존 nginx) setup.sh에 다른 포트를 지정하면 그만이다.

# docker-compose.yml
services:
  mediamtx:
    image: bluenviron/mediamtx:1.17.1
    volumes: [/etc/homecam/mediamtx.yml:/mediamtx.yml:ro]
    networks: [internal]              # 8889는 호스트에 게시하지 않는다
  caddy:
    image: caddy:2.11.4-alpine
    volumes:
      - /etc/homecam/Caddyfile:/etc/caddy/Caddyfile:ro
      - /etc/homecam/certs:/etc/homecam/certs:ro
    networks: [internal]
    ports: ["${TAILSCALE_IP}:443:443"]   # IP를 못박는다 — 아래 콜아웃

# Caddyfile
cam-vps.tailXXXXX.ts.net {
  tls /etc/homecam/certs/cam-vps.tailXXXXX.ts.net.crt \
      /etc/homecam/certs/cam-vps.tailXXXXX.ts.net.key
  handle /*/whip { reverse_proxy mediamtx:8889 }
  handle /*/whep { reverse_proxy mediamtx:8889 }
  handle { root * /var/www/homecam
           file_server }
}

5. 최종 방화벽 잠금 + 컨테이너 기동

ufw allow in on tailscale0
ufw allow 41641/udp   # WireGuard 전용 포트만 개방
ufw enable
docker compose up -d   # mediamtx·caddy 컨테이너 기동 (systemd 서비스 아님)
Docker와 방화벽

Docker는 ufw를 우회할 수 있다. Docker가 게시된 포트(-p/ports:)마다 자체 iptables 규칙(DOCKER 체인)을 심는데, 이 규칙이 ufw의 차단 규칙보다 먼저 매칭된다 — "0.0.0.0으로 연 포트는 ufw가 막아준다"는 네이티브 배포의 직관이 컨테이너 앞에서는 성립하지 않는다. 이 설계는 두 겹으로 막는다: ① Caddy의 443을 "${TAILSCALE_IP}:443:443"처럼 구체적인 IP에 못박아 바인딩한다 — Tailscale IP로만 바인딩된 소켓은 애초에 공인 인터페이스로 DNAT될 여지가 없다. ② MediaMTX의 WHIP/WHEP(8889)는 호스트에 전혀 게시하지 않고 내부 브리지 네트워크로만 둔다. 반대로 Tailscale 자체는 호스트에 네이티브로 남겨 이 우회 경로 자체를 만들지 않았다 — 이것이 "Tailscale은 컨테이너화하지 않는다"는 결정의 핵심 근거다.

단계별 구축 로드맵

각 단계는 수치로 정의된 통과 조건(Exit Criteria)을 만족해야 다음 단계로 넘어간다.

Phase 1 — 프로토타입 검증

VPS에 MediaMTX + Tailscale을 구축하고, PC 브라우저 두 탭으로 WHIP 게시 ↔ WHEP 재생 왕복을 검증한다.

통과 조건같은 VPS 내에서 게시 후 5초 이내 재생 화면 표시, 연속 10분 무중단.

Phase 2 — 실기기 페어링

구형 폰으로 홈 Wi-Fi에서 송출, 아이폰으로 LTE에서 시청. 코덱 정합성(§2.1) 검증이 이 단계의 관문이다.

통과 조건LTE 환경에서 화면·소리 동시 정상 출력, 지연 1초 이내, 30분 연속 무중단.

Phase 3 — 24시간 스트레스 테스트

발열(적외선 온도계 측정), 메모리 누수(Chrome 원격 디버깅으로 힙 사이즈 추이), 지연시간을 24시간 연속 기록한다. 동시에 §1.4의 트래픽을 실측해 온디맨드 전환 여부를 최종 판단한다.

통과 조건표면 온도 40°C 미만 유지, 24시간 후 힙 증가율 10% 미만, 재접속 3회 이하.

Phase 4 — 패밀리 롤아웃

가족 구성원 Tailscale 초대, PWA 설치 지원, 멀티 카메라 경로 분리(/livingroom, /bedroom).

통과 조건가족 전원이 QR 스캔만으로 3분 이내 시청 성공.
